# ADR-0007: Multi-tenant hosting architecture — reject fork-and-sync, migrate to edge-resolved config in phases

**Status:** Accepted
**Date:** 2026-07-06

## Context

Vibeverk's strategy (`docs/STRATEGY.md`) requires that a code change deployed once reaches every customer, and that onboarding customer N+1 not grow more expensive as N grows. The original plan was a single GitHub repo plus a single Supabase project serving all customers as true multi-tenant — this is why the `store` table still carries a vestigial `tenant_id` column (see CLAUDE.md's Supabase rules and `docs/architecture/roles-and-tenants.md`). The user confirmed this was ruled out by a combination of two constraints:

1. GitHub Pages binds only one custom domain per repository. Each customer needs their own real domain, not a subpath under one shared repo.
2. Keeping `tenant_id`-based RLS watertight across many customers in one shared Postgres database, exposed via PostgREST, was judged too risky to guarantee.

The resulting fallback — one repository fork plus one Supabase project per customer — is already the documented plan for the next customer (`docs/roadmap/ROADMAP.md` "Fase 2": new GitHub repo + Pages deploy + Supabase project). It solves the isolation problem but breaks the "deploy once, reach everyone" promise: today there is exactly one deployed instance (`hub/tenants.js` lists a single tenant), and no synchronization tooling exists at all (`.github/workflows/` contains only `test.yml`). A fork-per-customer model means every future shared-file fix — including security fixes — would need manual reapplication per customer fork, which is itself the kind of per-customer special-casing the strategy forbids, just relocated from code into git operations.

An Architect-agent investigation (read-only, no code changed) found supporting evidence: nearly every recent commit touches shared files (`core.js`, `module-*.js`, all four `index.html` entry points) together, and 23 `supabase/hotfix_*.sql` files were created in a single week (2026-07-01 through 2026-07-06), several fixing IDOR/RLS holes discovered during active development of the *current* single-tenant system. At this churn rate, "sync N customer forks after every shared-file commit" is not an occasional chore — it would be closer to a daily operational burden for a solo operator.

## Decision

**Reject fork-and-sync (git subtree/submodule/sync-bot across per-customer repo forks) as the long-term distribution strategy.** It optimizes the wrong layer, doesn't reduce operator burden as customer count grows, and has no tooling or lint today to prevent silent drift once a customer fork diverges (e.g. via bespoke tilbod-3 modules).

**Adopt a phased migration to an edge-hosting platform (e.g. Cloudflare Pages/Workers) that resolves customer configuration at request time from the `Host` header, instead of baking it into a per-repo static file at deploy time:**

- **Phase 0 (cheap, zero architecture risk):** Deploy the current, unmodified repo to Cloudflare Pages as a second host for the existing single tenant — same domain/SSL mechanics, same static `config.js`, same Supabase project. Proves the hosting-provider swap is a safe drop-in replacement for GitHub Pages before any code changes.
- **Phase 1 (separate, dedicated effort — not scoped by this ADR):** Make `config.js` loading asynchronous, resolved by the request's `Host` header via a Cloudflare Pages Function/Worker, instead of a synchronous `<script src="config.js">` baked into each repo. This touches `core.js` (the `window.SITE_CONFIG` read and an `App.ready` gate every module must wait on), every `module-*.js`/`intranet/module-*.js` IIFE, all four HTML entry points, and `console-core.js`'s write path (which currently writes tenant config to that tenant's own Supabase `store` table per repo). Config storage stays a flat file per tenant first — do not combine this with a "move config into Supabase" migration in the same step.
- **Phase 2 gate:** Only once Phase 1 is proven in production for the one real tenant does adding customer #2 become "drop a config file + add a DNS record" instead of "fork a repo." `docs/roadmap/ROADMAP.md`'s "Fase 2" (demo customer) should happen on this architecture, not as a throwaway fork — the demo customer is the cheapest available slot to validate the real target architecture for real, since there is no paying customer and no real stakes yet.
- **Permanent, independent of the above:** one Supabase project per customer is **not** reconsidered, regardless of hosting choice. The RLS risk on a shared database is judged higher today than before, given how many RLS/IDOR issues this session's own security remediation found even in the current single-tenant model (see `supabase/hotfix_*.sql`).

## Consequences

- The four HIGH security findings already tracked in `docs/roadmap/ROADMAP.md` "Current focus" (store anon-SELECT scope, write-policy over-permission, `chat_conversations` IDOR, `migration.sql` drift) still block Fase 2 regardless of which hosting path is chosen — this decision doesn't change that gate, and Phase 0 can start independently and in parallel with fixing them.
- Phase 1 touches `core.js`, the single highest-churn file in the repo, while it is also under active security remediation — it must be sequenced in isolation, not interleaved with unrelated feature work, and `test.js`/`test-intranet.js` must be extended to cover the async bootstrap path before it is relied on.
- The `Host`-header resolution mechanism is a new anon-facing security surface with no precedent in this codebase — resolving the wrong tenant would serve customer A's config (and potentially wire up customer A's Supabase project) to customer B's domain. This requires Security Auditor review before any second real customer depends on it; it is not a hosting detail.
- Migrating the *currently live* production tenant (vibeverk.no) to a new host/DNS is a real operational event (propagation, SSL reprovisioning) and should happen deliberately, only after Phase 0 has been stable for a period, not casually alongside other work.
- Genuinely open and not decided by this ADR: exact config-storage shape once it moves beyond a flat file (KV vs. Supabase vs. something else), and Cloudflare Pages Functions pricing/limits at eventual scale. These are small, deferred decisions to make when Phase 1 actually starts, not now.
- Tilbod-3 (bespoke module) customers are unaffected by this ADR's hosting question — they still require the customer to be on Workspace, and their `customModules` config mechanism (see `docs/STRATEGY.md`) works identically under either hosting model.

## Addendum (2026-07-07): hosting vendor evaluated — Vercel, not Cloudflare

This ADR's Decision section names "e.g. Cloudflare Pages/Workers" as an example, not a locked-in vendor choice. As part of restarting the SaaS-scaling effort (see the control-plane/data-plane ADR under preparation), the user explicitly required a real comparison — Cloudflare Pages/Workers, Vercel, and Netlify — before treating any vendor as decided, rather than accepting the ADR's original example by default.

**Comparison criteria**: multi-tenant custom-domain support, apex-domain (`kunde.no`) support without requiring the customer to migrate nameservers/DNS provider, subdomain support, request-time hostname resolution (edge functions/middleware), zero-build static hosting of the current repo, GitHub integration/preview deploys, pricing at 10/50/100-customer scale, vendor lock-in, and how automatable domain onboarding is from Console/API.

**Outcome: Vercel recommended over Cloudflare and Netlify.** The decisive factor is apex-domain handling:
- **Cloudflare**: a customer's bare apex domain (not just a subdomain) only works without a nameserver migration via "Apex Proxying," which is an **Enterprise-only add-on** (real-world Cloudflare Enterprise contracts land in the $5K–15K/month range) — unaffordable at 10–100-SMB-customer scale. Without it, customers must either migrate nameservers to Cloudflare or settle for a subdomain-style vanity domain instead of their own apex.
- **Netlify**: apex domains work technically (A/ALIAS/ANAME records), but Netlify's own documentation recommends *against* using an apex domain as the primary domain with an external DNS provider, for performance reasons — a shaky foundation for a core requirement.
- **Vercel**: apex domains work via a plain A record with *any* external DNS provider, no nameserver migration required, and "Vercel for Platforms" is a purpose-built multi-tenant product with a REST API for exactly this "one platform, many customer domains" shape — a direct fit for the semi-automated onboarding step (see the SaaS-scaling faseplan).

Edge-middleware maturity, GitHub integration/preview deploys, and pricing at this scale (all three land near $0–20/month for light SMB traffic) were judged roughly equivalent across all three and not decisive.

**Phase 0 (this ADR's, re-run against Vercel instead of Cloudflare) completed 2026-07-07**: the current, unmodified repo was deployed to Vercel (Hobby plan, for this test only — commercial use requires Pro) as a second host. User visually confirmed all four entry points (`/`, `/admin/`, `/intranet/`, `/console/`) render identically to the live GitHub Pages site. `vibeverk.no` itself was not touched and remains on GitHub Pages. Vercel's own deployment-protection gate (Vercel Authentication on preview URLs) blocked automated verification; confirmed manually instead.

**Not yet done, deliberately deferred rather than skipped**: an apex-domain-via-A-record test against a real (throwaway) domain — the user accepted Vercel's documented behavior as sufficient evidence for now rather than spending time on a live domain test at this stage — and a minimal edge-middleware Host-header echo test. Both should be picked up before Phase 1 (async config bootstrap) commits to Vercel-specific middleware syntax.

Everywhere else in this ADR that says "Cloudflare Pages/Workers" or "Cloudflare Pages Functions" should now be read as "the evaluated edge-hosting vendor (Vercel)" — the original text is left as-is per this repo's convention of not silently rewriting accepted ADR text, but this addendum is the current source of truth on which vendor.

## Addendum (2026-07-08): minimal edge-middleware mechanism-proof completed — Vercel confirmed viable, with one filename gotcha

The deferred "minimal edge-middleware Host-header echo test" from the 2026-07-07 addendum is done. `middleware.js` (repo root) reads the `Host` header, passes the request through unchanged via `next()` from `@vercel/functions`, and echoes the Host value in an `x-vibeverk-host-seen` response header — verified externally via a real HTTP request against a disposable Vercel test project (never `vibeverk.no`).

**Finding: Vercel Routing Middleware works correctly for this codebase's no-framework, no-bundler architecture — but only when the file is named `middleware.js`, not `middleware.mjs`.** Initial testing produced a fully reproducible negative result (no header, no invocation, no build-time error or warning) across 11 independently ruled-out variables: code correctness, lockfile state, every dashboard build setting, a completely fresh Vercel project, Deployment Protection, Fluid Compute, GitHub-integration vs. direct CLI deploy, and an explicit `"framework": null`. A same-account Next.js isolation test with the identical code then worked immediately, which was initially (incorrectly) read as proof that the no-framework architecture itself was the blocker — until an independent second review (Codex, reviewing the same debug report) correctly identified that the isolation test had changed two variables at once (framework, and the filename `.mjs` → `.js`) and could not isolate which one mattered. A controlled single-variable retest (same vanilla/static "Other" project, only the filename changed) confirmed: `.js` works immediately, `.mjs` silently doesn't. Vercel's own docs (`/docs/routing-middleware/api`) present `.mjs` as a documented equivalent to adding `"type": "module"` to `package.json` — that claim does not hold empirically for `Framework Preset: Other` projects.

**No architectural change follows from this.** The no-framework, no-bundler convention stands; no vendor reconsideration is needed. Phase 6 (real hostname→tenant→Supabase-project resolver) proceeds as originally planned, built as Vercel Routing Middleware, filename `middleware.js`. See `CLAUDE.md`'s "Known configuration" section for the standing rule this produced. The full debugging trail (all 11 ruled-out variables, both isolation tests, and the two-reviewer confound-catch) is preserved outside the repo in a scratch debug report and is not reproduced here in full.

Still genuinely open, unaffected by this finding: the actual tenant-registry shape (static JSON vs. Vercel Edge Config vs. Supabase), unknown-Host fallback behavior, and interaction with the already-completed async `App.ready()` config-bootstrap gate in `core.js` — these need their own Architect pass when Phase 6's real resolver logic is designed, and Security Auditor review remains required (per this ADR's Consequences section) before any second real customer depends on the resolver.

## Addendum (2026-07-09): Phase 6 implemented — real hostname→tenant resolver, config.js dynamically generated

The Architect was consulted again (read-only design pass) before implementation, per this repo's standing rule for architecture changes. Key design findings that shaped what follows, in the Architect's own words:

- **No `core.js` rewrite needed, and Phase 1 (async config bootstrap) turns out not to be a prerequisite either.** All four HTML entry points (`index.html`, `workspace/index.html`, `console/index.html`, `admin/index.html`) load the same relative `config.js` via a plain synchronous `<script src="config.js?v=N">` tag. Since the browser only needs *a* synchronous script at that URL that sets `window.SITE_CONFIG` — not specifically a static file — the entire Phase 6 change can live in **what bytes Vercel serves at `/config.js`**, not in how the browser loads it. `core.js`'s existing `App.ready()`/`markConfigReady()` gate (built for the originally-planned Phase 1) is untouched.
- **Two separate config layers exist, and Phase 6 only replaces one.** `core.js`'s `applySuperConfig()` already layers `superconfig`/`superconfig-private` (from the tenant's own data-plane `store` table, polled every 5s) on top of whatever base config loaded — this is the Console/broker-managed layer (ADR-0008/0009), unchanged by this work. Phase 6 only replaces the **base-skeleton layer**: what used to be a static, per-customer forked `config.js` is now generated per-request from the control-plane tenant registry.
- **A real circular dependency would have made this unbuildable as originally scoped**: `resolve_tenant_by_hostname()` only ever resolved `status = 'active'` tenants, but `activate_tenant` refuses until `routing_verified_at` is set — and the only credible way to *set* `routing_verified_at` is a real HTTP round-trip through the tenant's public hostname, which requires the RPC to already resolve the row. A `'provisioning'` tenant was unresolvable, so routing could never be verified, so it could never activate. Fixed by widening the RPC to also resolve `'provisioning'` tenants (not `'suspended'`/`'archived'`).
- **No hostname-uniqueness guard existed** (`slug` is `UNIQUE`, `hostnames` was not) — an accidental collision between two tenants' hostnames would have been a real cross-tenant config leak via this same RPC. Fixed with a `BEFORE INSERT OR UPDATE` trigger using Postgres's array-overlap (`&&`) operator, since a plain `UNIQUE` constraint can't express "unique elements across an array column."
- **Case sensitivity**: HTTP `Host` headers are case-insensitive; array membership is a literal string comparison. Hostnames are now normalized to lowercase on write (the same trigger) and the RPC lowercases its input.

**What was built** (all in `supabase-control/supabase/migrations/20260709170108_phase6_hostname_resolver_hardening.sql` and the two files below — code only, not yet deployed anywhere, per the standing deployment safeguard):

- `resolve_tenant_by_hostname()`: widened status filter, case-insensitive comparison, and now also returns `data_plane_storage_key` (needed by the generated `config.js` below; still an explicit column list, never `SELECT *`).
- New `tenant-admin` action `verify_tenant_routing`: for every hostname registered to a `'provisioning'` tenant, makes a real server-side `fetch("https://" + hostname + "/config.js")` (never a client-supplied claim) and confirms both a 200 response AND that the body actually names *this* tenant's `data_plane_url`/`data_plane_anon_key` — the anti-collision check, complementing the write-time hostname-overlap trigger above. Sets `routing_verified_at` only if every hostname passes; clears it to `NULL` on any failure so a stale pass can't linger. Hostname inputs are validated against a domain-name-shape regex before any outbound fetch is attempted (same SSRF-adjacent concern the Security Auditor previously flagged for `data_plane_url`, applied here to the new outbound-fetch target).
- New `api/tenant-config.js` (Vercel Function): calls `resolve_tenant_by_hostname()` for the request's `Host` header and returns `window.SITE_CONFIG = {...}` as `application/javascript` — a minimal base skeleton (Supabase URL/anon key, `storageKey`, `productMode`, `features`/`intranettFeatures`, `theme`). **Deliberately does not attempt full per-tenant branding parity** (company name/logo/admin password/analytics/etc.) — those aren't in `resolve_tenant_by_hostname`'s columns and aren't populated by `register_tenant`/`update_tenant_connection` today. The existing superconfig/broker layer already supplies real branding after activation, the same way it does for today's one real tenant; full dynamic branding is explicitly deferred as separate, later work, not silently scoped into this change.
- `middleware.js` rewritten from the Host-echo mechanism-proof to the real implementation: unconditionally rewrites `/config.js` to `/api/tenant-config`, and for page-level requests (matcher covers `/`, `/config.js`, `/workspace(/)`, `/console(/)`, `/admin(/)`) resolves the tenant itself so an unregistered hostname gets a real 404 instead of `index.html` rendering against a null `window.SITE_CONFIG` (which `core.js` is not guarded against). Still filename `middleware.js`, never `.mjs`, per this ADR's 2026-07-08 addendum.
- Console: the previously-greyed-out "5. DNS / gå-live" checklist card now calls `verify_tenant_routing` for real and displays per-hostname results; "6. Set aktiv" is gated on the resulting `routing_verified_at` exactly as before.

**Sequencing, per the Architect's explicit recommendation**: Phase 6 does **not** require or wait on migrating `vibeverk.no` off GitHub Pages. It should be built and proven against a throwaway/canary domain pointed at a disposable Vercel project, backed by the `vibeverk-staging` Supabase project (created 2026-07-09, see `docs/project/CHANGELOG.md` 0.23.0) as its data-plane — never against `vibeverk.no` or any real customer. `vibeverk.no`'s own cutover remains a separate, later, explicitly-approved decision.

**SQL migrations deployed and verified live 2026-07-09** (both via Dashboard SQL Editor, followed by direct verification queries per this repo's own standing rule, not just a clean "Success" message):
- `supabase/migrations/20260709193227_add_rls_check_to_schema_fingerprint.sql` applied to `vibeverk-staging` — confirmed `verify_schema_fingerprint()`'s new signature includes `rls_enabled`, and a real call against staging returned `rls_enabled = true` for all 5 expected tables.
- `supabase-control/supabase/migrations/20260709170108_phase6_hostname_resolver_hardening.sql` (plus the still-pending `20260709160626` from the prior round) applied to the real `vibeverk-control` project — `vibeverk-control` has no staging replica of its own, so this went straight to the real control plane after the pre-check confirmed zero `tenants` rows would violate the new `data_plane_url` CHECK constraint. Confirmed: `resolve_tenant_by_hostname()`'s new signature (including `data_plane_storage_key`), the `tenants_hostname_overlap_guard` trigger, `schema_verified_at` column, and the atomic `store_tenant_service_role_key()` are all live. The one real tenant row's `hostnames` (`vibeverk.no`) is present and already lowercase.
- `tenant-admin`/`broker` Edge Functions redeployed to `vibeverk-control`, verified live via negative-path checks (401 with no auth on both).

**Live Vercel deployment test completed 2026-07-09**, resolving the "no live deployment test yet" gap above. Reused the existing `vibeverk-j1yg` Vercel project (the same one used for the earlier `.js`-vs-`.mjs` middleware isolation test, already on `Framework Preset: Other`) rather than provisioning a new one or buying a domain — its own `vibeverk-j1yg.vercel.app` address is a real, publicly resolvable hostname, at zero cost and with no DNS step required. `VIBEVERK_CONTROL_URL`/`VIBEVERK_CONTROL_ANON_KEY` env vars set (Production + Preview) and the repo deployed via `vercel --prod`.

**Real bug found and fixed during this**: the Vercel CLI's `env add` with a piped stdin string (`"value" | vercel env add NAME env`) silently saved an **empty** value on this CLI version/setup, despite printing "✓ Added" and even reporting "Removed trailing newline from stdin input" — a clean, no-error confirmation that was simply wrong, the same class of false-confidence signal this repo has already hit with Supabase's Dashboard SQL Editor. First deploy attempt 502'd with `TypeError: Invalid URL string` inside `api/tenant-config.js`, traced to `process.env.VIBEVERK_CONTROL_URL` being empty. Fixed by using `vercel env add NAME env --value "..." --no-sensitive` instead (an explicit non-interactive flag, confirmed via `vercel env pull` showing the real value before redeploying) — **lesson: never trust a piped-stdin CLI confirmation for a value you haven't independently read back.**

Both the page-level gate and the `/config.js` rewrite verified against the real deployment for the negative case (unregistered hostname): `curl -i https://vibeverk-j1yg.vercel.app/` → real 404 with the middleware's own "not a Vibeverk customer" message (not `index.html`); `curl -i https://vibeverk-j1yg.vercel.app/config.js` → 404 with `window.SITE_CONFIG = null;` and a console error, exactly as designed.

**Still not done**: the positive-path end-to-end test (register a canary tenant, point it at `vibeverk-staging`, run the full register → connection → secret → schema-verify → routing-verify → activate chain, and confirm a real browser visit renders a working page against `vibeverk-j1yg.vercel.app`) — requires either a live Console session (OTP email round-trip) or a directly-authenticated API call as the superadmin operator, neither done yet this round.

### Pre-merge Security Auditor review of Phase 6 (2026-07-09)

A Security Auditor pass over this branch's diff, requested by the user before merge, returned verdict **CAUTION** (not the clean PROCEED of the two prior control-plane rounds) — 2 HIGH, 1 MEDIUM, 2 LOW, no BLOCKER. All five fixed on the same branch before merge:

- **H1 — `HOSTNAME_RE`'s own comment claimed it rejected bare IP literals; it didn't.** `127.0.0.1`/`169.254.169.254` (a cloud metadata address) satisfy the domain-shape regex fine, since digits are valid label characters — handing `verify_tenant_routing`'s real outbound `fetch()` an SSRF-adjacent target for an already-superadmin caller. Fixed: a new `IPV4_LITERAL_RE` rejects bare IPv4 hostnames outright, and a new `assertHostnameSafeToFetch()` additionally resolves the hostname's DNS server-side and rejects private/loopback/link-local ranges before any fetch. DNS-rebinding (the resolved address changing between this check and the `fetch()` a moment later) is **not** fully closed — accepted residual risk given the action's existing superadmin gate and full audit logging.
- **H2 — widening `resolve_tenant_by_hostname()` to `'provisioning'` tenants exposes a tenant's real hostname and real Supabase credentials publicly before RLS is meaningfully verified.** `verify_tenant_schema` previously only confirmed expected tables *exist*, not that RLS was enabled on them — a freshly-provisioned project with RLS not yet turned on would still pass. Fixed: `verify_schema_fingerprint()` (the customer-project-side RPC, extended by new migration `supabase/migrations/20260709193227_add_rls_check_to_schema_fingerprint.sql`) now also reports `rls_enabled` per table via `pg_class.relrowsecurity`; `verify_tenant_schema` requires it alongside table existence before setting `schema_verified_at`. This narrows but doesn't eliminate the exposure window (a tenant is still resolvable, and its hostname still publicly reachable the moment DNS points there, purely by being `'provisioning'` — `schema_verified_at` only gates `activate_tenant`, a separate later step) — accepted for now given the canary-only near-term plan, to be revisited before any real customer's hostname goes live.
- **M1 — the new hostname-uniqueness trigger was a real TOCTOU race.** Two concurrent `register_tenant` calls with overlapping hostnames could both pass the trigger's `EXISTS` check under READ COMMITTED before either committed. Fixed with a fixed-key `pg_advisory_xact_lock` serializing all hostname-mutating transactions — coarse-grained, but hostname registration is rare and superadmin-only.
- **L1/L2** — the migration's `DROP`+`CREATE` of `resolve_tenant_by_hostname()` was missing the standing `NOTIFY pgrst, 'reload schema'` rule; `verify_tenant_routing`'s outbound fetch had no timeout or response-size bound. Both fixed (5s `AbortController` timeout, 64KB streamed-read cap).

Full finding detail preserved in `tenant-admin/index.ts`'s own header comment and the two migration files' inline comments, not repeated here. `node test.js`/`node test-workspace.js` re-run clean (504/1, 151/1) after all five fixes.
